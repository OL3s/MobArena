# Agent Guide

This directory is primarily for AI agents working on MobArena. Use it to preserve project context, avoid repeated discovery work, and keep future changes consistent.

## Current Project State

- This is a minimal Godot 4.6 C# project.
- Use C# for gameplay and UI scripts unless the user explicitly requests otherwise.
- `project.godot` is the source of truth for current engine-level settings.
- `MobArena.csproj` is the Godot C# project file.
- `GlobalOverlay` is autoloaded from `autoload/overlay/GlobalOverlay.tscn` for blurred popups and modal overlays.
- `SaveNode` is autoloaded from `autoload/SaveNode.tscn` for temporary runtime company data and shared town time between scenes. It is not persistent storage yet.
- `LocalInputConfig` is autoloaded from `autoload/LocalInputConfig.tscn` for runtime local input/controller setup. It reads user-facing input preferences from `SaveNode.SettingsConfig` and exposes `ControllerSetups` for UI to render.
- The game concept comes from `../GameIdeas/MobGladiator.md`.
- `docs/game-design.md` contains the local implementation-oriented summary of that concept.
- Active backlog and milestone planning live in GitHub issues for this repository. Check the GitHub issues and milestones together with `docs/focuspoint.md` before choosing the next implementation task.
- The initial scene flow is `scenes/main_menu.tscn` to `scenes/town.tscn`. Roster management is folded into the town through the town-center `RosterYard`; the old separate Roster Hall scene path has been removed. Town buildings currently open modal overlay packed scenes.
- Roster management should stay centered on an in-town open area where current gladiators are visible idling and can be dragged into management sections. Aim for Training Hall on the left, Thermae/treatment on the right, and clear access to market functions for new gladiators and equipment work.
- `scenes/town.tscn` and `scenes/arena.tscn` both use neutral roots with a separate `Node2D` world and `CanvasLayer` controller UI.
- Town uses an implied horizontal-road layout with 1:1 buildings as `Node2D` instances of `scenes/components/town/TownBuilding.tscn` arranged in a 3x2 grid. The road is layout space only and is not drawn.
- `TownBuilding` has exported `PackedScene` targets for `OverlayToOpen` and `SceneToOpen`. Use `OverlayToOpen` for town building UI that should stay over town; reserve `SceneToOpen` for future full-scene navigation only when there is a concrete need.
- `TownBuilding` visuals are per-instance exported textures: `BuildingTexture` and `IconTexture`.
- Town UI should represent champion pressure as time remaining before a mandatory champion fight deadline, not as a simple number of arena fights completed.
- Town phase is arena-first and has only Day and Night. Day is preparation before arena combat; returning from arena moves the run to Night; the `Next Day` button is disabled during Day and enabled at Night.
- Town and arena visual environment uses `scenes/components/environment/EnvironmentVisualOverlay.tscn`. Keep time-of-day visuals separate from weather: `TimeOfDayVisual` follows `TownPhaseState`, while weather lives in shared `scripts/resources/WeatherState.cs` so combinations like Night + Rain remain possible and current weather carries between scenes and save/load. The overlay lives above world rendering and below HUD/UI.
- Phase state belongs in `scripts/resources/TownPhaseState.cs`; the shared runtime instance is `SaveNode.TownPhaseState`.
- Phase transition orchestration belongs in `scripts/resources/PhaseTransitionController.cs`, not in HUD or room scripts. It owns Day -> Night and Night -> Day transition flow and calls company phase work.
- Weather changes should go through `WeatherState` and phase-time advancement should randomize weather through `PhaseTransitionController`, not through scene-local randomization. `EnvironmentVisualOverlay` applies the shared weather to both color tint and `WeatherShaderLayer` shader effects. Weather randomization is phase-aware: Rain is 15% for both Day and Night, Night never picks Sun, and Day splits the remaining chance between Clear/cloudy and Sun. Keep weather effects in `assets/shaders/Weather*.gdshader` resources and have `WeatherShaderLayer` switch materials for the active weather. Clear weather should stay subtle with broad moving cloud shadows. Sun should feel hot with moving flare/shimmer. Composite multi-part weather, such as rain, with separate layer materials for background clouds, falling rain, and foreground splashes instead of packing every effect into one shader.
- Future phase transition animation should be coordinated from `PhaseTransitionController` or a small helper it owns/calls, because the transition is gameplay time advancement rather than scene-local button behavior. Do this later as UX polish; keep current phase mutation APIs authoritative.
- Time-passes effects are explicit phase-transition work, not continuous time. They execute once on Day -> Night and once on Night -> Day through `CompanyRunData.ExecutePhaseBuildingWork`: courtyard/arena gladiators recover 2 exhaustion and 10% max health, Thermae-assigned gladiators pay gold for the selected health or exhaustion treatment, and Training Hall work spends gold, stamina, and exhaustion to add attribute XP for the selected focus. Night -> Day also pays gladiator salary through `CompanyRunData.PayNightSalary`, currently the floor of each gladiator's initial cost divided by 10.
- Company logo selection belongs in `scripts/resources/CompanyLogoData.cs`. Use `CompanyLogo.tscn` to render shield and inner logo layers. Logo identity includes shield shape, shield color, logo icon, logo size, and company name. Keep random company-name word lists in `scripts/resources/CompanyNameGenerator.cs`, not inline in `CompanyLogoData`. In town, shield clicks should open `CompanyOverviewOverlay.tscn`; use its `Edit Company` action to open `CompanyLogoEditorOverlay.tscn` through `GlobalOverlay`. Do not add persistence beyond the existing save resource flow yet.
- Company run state belongs in `scripts/resources/CompanyRunData.cs` and is separate from career totals. Track frequent mutable values there, including current gold, the current active `GladiatorData` list, current cemetery list, equipment inventory, town assignments, arena control assignments, and current run mob kills. New company runs should go through `SaveNode.StartNewCompanyRun()`, which starts with no gladiators; recruitment should happen through the Market and `CompanyRunData.AddGladiator` so `CompanyCareerData.TotalGladiatorsInCareer` stays correct. `AliveGladiators` is derived from the active gladiator array. Use its methods for changes such as `AddGladiator`, `AddGold`, `TrySpendGold`, `AddMobKilled`, and `KillGladiator`.
- Completed company history belongs in `scripts/resources/CompletedCompanyHistory.cs`, not in scene-local UI. It stores capped, fame-sorted `CompletedCompanyRecord` resources containing the completed company identity, career totals, and final fame only; do not store full `CompanyRunData` there. End-of-run flows should call `SaveNode.TryAddCurrentCompanyToCompletedHistory()` so only qualifying fame records are saved and sorted consistently.
- Current roster capacity lives on `CompanyRunData.GladiatorCapacity` and defaults to 6. Use `CanAddGladiator`, `AddGladiator`, and `TryBuyGladiator` for add/buy flows so the cap is enforced before spending gold or mutating market stock.
- Current spendable fame belongs on `CompanyRunData.Fame`, not career totals. Mutate it through `CompanyRunData.AddFame`, `LoseFame`, and `TrySpendFame`; `LoseFame` clamps at zero. Town HUD wealth displays current gold and current fame together. Fame should be awarded when contracts are won, scaled by contract difficulty and any future contract-specific fame modifiers.
- Fame donation pricing and mutation belong in `CompanyRunData`, not the Arena overlay. Use `GetFameDonationGoldCost`, `CanDonateForFame`, and `TryDonateForFame` for the Arena `Donate` flow so buying fame spends gold and updates current fame through one backend path.
- Enemy mob metadata belongs in Godot `.tres` resources under `resources/mobs/`. Use `scripts/resources/mobs/MobData.cs` for shared display data and `EnemyMobData.cs` for enemy-specific stats. Contract/codex UI should reference the `.tres`; combat spawning should use the resource's packed scene once runtime enemy scenes exist. Do not duplicate enemy stats directly in contract cards.
- Arena contract metadata belongs in `resources/contracts/` using `scripts/resources/contracts/ArenaContractData.cs`. Contracts should reference enemy mob `.tres` resources in their `Mobs` array and store fame scaling cost plus gold reward there, not as parallel hardcoded UI tuples. Net fame comes from `GetNetFameReward(currentCompanyFame)`, which subtracts a current-fame-based cost from the summed mob fame values. Contract UI should group duplicate enemy resources for display instead of showing repeated copies of the same mob icon.
- `CodexOverlay` should discover authored resource files from `resources/mobs` and `resources/items`; do not maintain a separate parallel codex registry unless there is a concrete filtering/unlock requirement. New enemy or item `.tres` files should appear in the codex automatically if they derive from `MobData` or `ItemData`.
- Gladiator death should go through `CompanyRunData.KillGladiator` so death vitals, active roster removal, cemetery insertion, career death totals, `RunChanged`, and `GladiatorDied` stay consistent. Do not use a separate dead flag on active gladiators; a dead gladiator is one that has been moved from `Gladiators` to `Cemetery`. Town UI listens for `GladiatorDied` and opens `scenes/ui/GladiatorDeathOverlay.tscn` with the dead gladiator card. Company overview's `Cemetery` button opens `scenes/ui/CemeteryOverlay.tscn` to list `CompanyRunData.Cemetery`.
- Legacy supply upkeep, continuous town time, and champion deadline timer pressure have been removed for the arena-first loop.
- `GladiatorData` owns gladiator condition values and caps. `Exhaustion` is the only exported 0-10 management condition. New default gladiators roll exhaustion in the 6-10 range and current health from 20-100% of max health. Low exhaustion caps recoverable health and stamina; values at 5 or above apply no cap penalty, then the multiplier scales from 1 down to 0 between 5 and 0. Current health and stamina should be restored through gladiator methods so they respect those recoverable caps.
- Reuse `scenes/components/ui/GladiatorCard.tscn` for compact gladiator presentation. The first roster list overlay is `scenes/ui/GladiatorsOverlay.tscn` and should display `CompanyRunData.Gladiators` horizontally.
- Current gladiator equipment data is still placeholder-level. Future equipment work should replace armor, main item, and second item strings with authored Godot `.tres` resources, while keeping the signature skill enum on equipment unless a fuller skill resource system is introduced.
- Company career totals belong in `scripts/resources/CompanyCareerData.cs` and are separate from frequent current state. Track long-term additive values there, including total gladiators in career, gladiators dead, total gold earned, contracts completed, mobs killed, and champions defeated.
- `SaveNode` should remain the runtime holder and persistence boundary. Do not put gameplay mutation helpers there; `HasSave()`, `Save()`, `Load()`, `DeleteSave()`, and `ResetRuntimeState()` manage the simple Godot resource save under `user://save`.
- `SaveNode.Get()` is intentionally strict and throws if the autoload is missing. Save-data delete actions should return to `scenes/main_menu.tscn` after successful deletion so active town, roster, arena, or overlay scenes do not continue running against reset save resources.
- Autosave should remain lightweight and deliberate. Current save triggers are company create/edit, app exit through `SaveNode._ExitTree`, pressing Back from town to main menu through `Town.cs`, returning from arena, and advancing Night -> Day from `TownHud`.
- Settings resources that should eventually persist with save/profile data belong on `SaveNode`. Current settings are in `scripts/resources/SettingsConfig.cs`, exposed as `SaveNode.SettingsConfig`.
- The temporary project-wide debug flag belongs in `SettingsConfig.DebugEnabled`, not in a separate autoload. Settings UI should mutate it directly like the other settings fields; gameplay code can read `SaveNode.DebugEnabled` as a convenience. Debug-only town controls should stay gated behind this flag, such as the compact Town HUD `Dev` menu.
- Local input controller rows are represented by `scripts/resources/LocalInputControllerConfig.cs`. Do not hardcode connected-device rows directly in UI scenes; refresh and read `LocalInputConfig.ControllerSetups` instead.
- Main menu should keep `Enter Town` disabled until `SaveNode.HasCompany` is true. The company editor should allow cancel only when company data already exists.
- Main menu top-right controls use `Codex`, `Records`, and `SettingsButton.tscn` for reusable settings feedback. Arena participant/controller mapping is resolved per contract launch from the Arena overlay, not finalized in the main menu.
- `.godot/` is ignored and should be treated as local editor state.

## Development Guidelines

- Prefer small, focused changes that establish useful structure without overbuilding.
- Do not invent gameplay systems, folder structures, or architecture unless the user asks for them.
- Keep documentation factual. If a feature does not exist yet, describe it as planned or absent rather than implying it is implemented.
- Favor the first prototype loop before adding broader management systems: one gladiator, one arena, slimes, movement, attack, contract reward, death, and replacement. `resources/mobs/green_slime.tres` is the starter enemy metadata template; assign its packed scene only once an actual slime actor scene exists.
- When management systems are added, balance upkeep costs against arena income. Resting over time is cheaper with a small roster, Thermae speeds health or exhaustion recovery for gold, stamina cannot be treated there, and Training Hall spends gold plus stamina to train gladiators.
- Reward and combat systems should call run-data methods for current changes and career-data methods for lifetime-only events. They should not subtract from career totals when current state changes. Use `CompanyRunData.AddGold` for earned gold, `CompanyRunData.TrySpendGold` for spending current gold, and `CompanyRunData.AddMobKilled` when a mob dies during the current run.
- Use `PhaseTransitionController.CompleteArenaContract` when a real or mocked arena contract finishes: it runs Day -> Night work, applies fight exhaustion to arena-assigned gladiators, returns them to the courtyard, and clears arena control assignments. Use `PhaseTransitionController.CompleteArenaDay` only for generic/debug Day -> Night advancement and `PhaseTransitionController.AdvanceToNextDay` for Night -> Day from the HUD. Use `TownPhaseState` APIs for direct phase UI behavior: `GetDayLabel`, `GetPhaseLabel`, `GetPhaseProgressValue`, `GetPhaseProgressMax`, and `CanAdvanceToNextDay`.
- Treat phone, controller, and desktop compatibility as a baseline requirement for input and UI decisions.
- Arena control setup is explicit per contract launch. `LocalInputConfig` should not auto-create startup controller setups; it records only the controllers joined during the current arena launch flow.
- Controller join logic belongs in `LocalInputConfig`, while `ArenaControlConfigOverlay` owns the per-launch UI flow and maps joined controllers to assigned Arena gladiators.
- Keep town and arena scene logic split between `World` for game-space nodes and `ControllerUi` for HUD, controller navigation, touch controls, and overlays.
- Town HUD top resources focus on company status, spendable gold/fame, and roster Risk warnings. Risk display should use `GladiatorData.GetRiskStatus(...)` so one risky gladiator produces one icon/count only: exhausted, low health, or critical for both. Idle assigned gladiators are counted separately through `CompanyRunData.GetIdleAssignedGladiatorCount`. The clock icon means assigned but no work will run this phase; exhausted uses `assets/ui/gladiator_icons/exhaustion.svg`. Low-health uses `SettingsConfig.LowHealthWarningRatio`.
- The town HUD bottom phase action is authored directly in `TownHud.tscn` as `PhaseActionButton`. During Day it emits `SelectContractPressed` and should open the same Arena building/contract flow as clicking the Arena building; during Night it advances to the next day. Do not reintroduce hidden speed/pause/timeline nodes and runtime hide calls.
- Champion cadence is tracked from `TownPhaseState`: every seventh day is Champion Day. Current UI exposes this as a calendar row (`Champion in X days` or `Champion Day!`); future contract filtering should use the same phase-state APIs.
- Author room layouts as real `.tscn` node trees. C# should wire behavior, signals, and scene transitions rather than constructing whole room layouts at runtime.
- Prefer decoupling and deconstructing repeated pieces into reusable `.tscn` components instead of duplicating behavior in parent scene scripts.
- Town buildings should stay as reusable `Node2D` components with `Area2D` interaction, SVG visuals, an icon, and an in-scene label. Do not regress them to plain `Button` nodes.
- Town buildings can use `DisableWhenRosterEmpty`. Keep Market available, but non-market buildings should gray out, suppress hover panels, and ignore interaction when `CompanyRunData.Gladiators` is empty so the player is directed toward recruitment.
- Upgradeable behavior should use `IUpgradeable`. Current upgradeable buildings are Thermae and Training Hall through `BuildingOverlayPanel`; persistent levels and costs belong in `CompanyRunData`, not scene-local fields. Overlay buttons should call `TryUpgradeBuilding` so gold spending and upgrade-level mutation stay centralized.
- Town drag/drop is a core town interaction system and should be treated as the default path for physical town management actions. It is coordinated by `scenes/components/town/RosterYard.cs`. Draggable payloads are represented by `TownDragPayload` and `TownDragPayloadKind`; current kinds are Gladiator and Item. Drop receivers implement `ITownDragDropTarget`, expose `AcceptedTownDragDropKinds`, and register in `RosterYard.DragDropTargetGroup`. Use `TownDragDropRules` for shared accepted-kind checks, viewport hit tests, all-kind arrays, and debug message formatting rather than duplicating those checks.
- RosterYard's compact gold button previews current phase total near the button, current building phase costs in both phases, and salary on visible roster-yard gladiator avatars. Salary displays 0 during Day and the next Night -> Day salary during Night. Building hover badges show the building's own phase cost plus salary for gladiators assigned inside that building through `CompanyRunData.GetTownLocationPhaseGoldPreviewCost`. Pressing the gold button opens `GoldCostOverlay`, which discovers `IPhaseGoldCostSource` nodes and lays out visible current-phase costs in side-by-side boxes for gladiators, buildings, and payment result. Building previews reuse the centered `SellPreview` gold badge so they appear where occupancy badges normally appear; while visible, the cost preview takes priority over occupancy. The Night `Next Day` button must stay disabled when `CompanyRunData.CanPayCurrentPhaseGoldCost` is false. Scene previews can use `IPhaseGoldCostSource`, but backend affordability must stay in `CompanyRunData` so phase transitions are safe without relying on loaded scene nodes.
- The Town HUD `Select Contract` action and arena contract launch must validate `CompanyRunData.CanPayArenaReturnUpkeep`, because returning from arena completes Day -> Night and immediately charges current phase upkeep. If the company cannot afford that return upkeep, the Town HUD action should be disabled and the arena start button should show `Upkeep Short`.
- If multiple town drop targets overlap, `RosterYard` sends the payload to the highest `TownDragDropPriority`. Roaming `RosterYardGladiator` targets use a higher priority than default buildings so dropping onto a gladiator does not accidentally hit a building behind them.
- Town location assignment state belongs in `CompanyRunData.TownAssignments`, not scene-local building arrays. `CompanyRunData.Gladiators` remains the owned active company roster; `TownAssignmentData` stores explicit location lists for courtyard, arena, Thermae, and training hall. `RosterYard` displays only `TownAssignments.CourtyardGladiators`. External callers should mutate assignments through `CompanyRunData.TryAssignGladiatorToTownLocation`, `TryMoveGladiatorToCourtyard`, and `RemoveGladiatorFromTownAssignments` so the active roster is validated before location lists change. Use `TownBuilding.TryTakeGladiator`, `CanTakeGladiator`, `RemoveAssignedGladiator`, and `ClearAssignedGladiators` from building/drop code rather than mutating arrays directly. A gladiator should be in exactly one town assignment list at a time. `MaxAssignedGladiators` controls fixed-cap buildings. Arena control assignments are configured per contract launch by pressing Enter, touch, or gamepad A in `ArenaControlConfigOverlay`. Market uses `SellDroppedPayloads` and should not rely on assignment for selling.
- Occupied town buildings show a centered occupancy badge with a gladiator icon and assigned count/capacity. Keep this badge tied to `CompanyRunData.RunChanged` so it reflects central assignment state, not scene-local assumptions.
- Building overlays based on `BuildingOverlayPanel.tscn` can show assigned gladiators with `ShowAssignedGladiators = true` and an `AssignmentLocation`. Arena, Thermae, and Training Hall overlays use this to show `[grab icon][gladiator][gladiator n+1]` inside the overlay, not on the town building sprite. Thermae and Training Hall overlays also use `BuildingOverlayPanel` focus selectors. Dragging one of those portrait buttons closes the overlay and calls `RosterYard.StartGladiatorDrag`; if the drag is released over no valid target, `RosterYard` returns the gladiator to the courtyard through `CompanyRunData.TryMoveGladiatorToCourtyard`.
- The Market town building uses `SellDroppedPayloads = true`. Dropping an item or gladiator onto the Market sells it through `CompanyRunData.TrySellItem` or `TrySellGladiator`, and the building shows a gold preview through `SetTownDragDropPreview` while dragging over it. Keep real sell mutations in run/resource APIs, not in UI-only scripts.
- Market drag/drop sales must confirm before mutating run state. `TownBuilding` uses `GlobalOverlay.ShowGoCancelPopup` to ask whether to sell the payload for the current previewed gold value; the confirmed action then calls the relevant `CompanyRunData.TrySell...` API. Keep stale-payload validation in the run-data API even when the UI confirmation already showed a value.
- Drop receivers must validate that payloads still exist in current run state before mutating state; print clear `GD.PushError` messages when a dragged item or gladiator no longer exists in inventory/roster. This is intentional early bug detection for stale drag payloads and mismatched UI state.
- Gladiator removal paths must return equipment through `CompanyRunData.ReturnGladiatorEquipmentToInventory` before removing or destroying the gladiator. `TrySellGladiator` and `KillGladiator` already do this; future destroyed, retired, or transferred-gladiator APIs should call the same helper instead of duplicating equipment-return logic.
- Gladiator attribute levels are EXP-derived on `GladiatorLevelData`. Use the per-attribute APIs and `TotalExp`/`TotalLevel` instead of manually summing or treating signature moves as leveled skills. Signature moves remain simple identity values on `GladiatorEquipmentData`.
- Item purchases must keep the original `Cost`; gladiators keep `InitialCost` as base value. Gladiator buy/sell pricing should use `GladiatorData.GetMarketValue()` / `GetMarketSaleValue()` so current health, stamina, and exhaustion affect both hiring cost and resale value.
- Do not use a `Node2D` root for scenes that also own controller UI. Use a neutral `Node` root, with `World` and `ControllerUi` as siblings.
- Author world layouts in the `1152x648` frame. Use centered `Camera2D` nodes for scenes with a `World` node so wider/taller aspect ratios expand from the center through engine scene behavior, not resize code.
- Use `GlobalOverlay.ShowBlurredPopup` for informational modal text and `GlobalOverlay.ShowGoCancelPopup` for confirmation flows.
- Use `GlobalOverlay.AddOverlay` for custom overlay scenes. Custom overlays that should visually match popups can reuse `assets/shaders/PopupBlurBackdrop.gdshader` on a fullscreen `ColorRect`. Do not add scene-local overlay managers; `GlobalOverlay` is the single overlay path.
- Preserve Godot-generated file formats and avoid hand-editing generated files unless there is a specific reason.
- Keep repository files text-normalized with LF line endings.

## Godot Notes

- Project name: `MobArena`
- Config version: `5`
- Feature tags include `4.6` and `GL Compatibility`.
- Windows rendering device driver is set to `d3d12`.
- Rendering method is `gl_compatibility` for desktop and mobile.
- 3D physics engine is set to `Jolt Physics`.

## Before Changing Code

1. Inspect the current tree. This project may grow quickly from its initial state.
2. Read `docs/focuspoint.md` and check the GitHub issues/milestones for current priority and issue-specific acceptance notes.
3. Check whether scenes, scripts, or assets already exist before creating new ones.
4. Prefer following existing naming and folder conventions once they are established.
5. If conventions are absent, use standard Godot project organization and document the choice.
